## 제안요청서의 문장은 어떻게 인프라가 될까?
“내부 시스템은 Private Network로 구성한다”, “트래픽 증가에 대응할 수 있어야 한다”, “장애가 발생하면 다른 서버로 전환할 수 있어야 한다.”
제안요청서에는 이런 문장들이 등장한다. 실제로 구축하려면 여기서 한 단계 더 들어가야 한다. 어떤 서버를 내부에 둘지, 외부 사용자는 어디로 들어올지, 어느 계층을 늘릴지, 장애가 났을 때 무엇이 대신 동작할지를 정해야 하기 때문이다.
2026년 2월 클라우드스퀘어 현장실습에서 나라장터의 COSS/HUSS 허브 LMS 제안요청서를 바탕으로 1인 프로젝트를 진행했다. 요구사항을 분석하고, 네이버 클라우드 플랫폼(NCP)에 LMS를 위한 인프라를 설계·구축했다. 서비스 요청이 흐르는 모습을 확인할 수 있도록 React와 Spring Boot로 시연용 LMS도 직접 구현했다.
이 글은 공개된 제안요청서를 설계 과제로 삼아 진행한 실습 기록이다. **요구사항을 어떤 구조로 해석했고, 왜 그 구성을 선택했는지**를 중심으로 정리한다.
![나라장터 제안요청서 기반 프로젝트 주제](/notion-assets/ncp-lms-cloud-architecture/image-001.png)
프로젝트의 출발점이 된 「2025년도 첨단분야 혁신융합대학 COSS/HUSS 허브 LMS 교육 플랫폼 및 클라우드 유지보수 및 운영지원」 제안요청서이다.
## 먼저 전체 구조부터 보기
![NCP 기반 COSS/HUSS 허브 LMS 클라우드 인프라 아키텍처](/notion-assets/ncp-lms-cloud-architecture/image-002.png)
전체 아키텍처는 사용자 서비스, 관리자 접근, 콘텐츠 제공, 배포 트래픽을 나누어 읽으면 이해하기 쉽다.
- 사용자 서비스: 외부 L7 Load Balancer를 거쳐 WEB, 내부 L4 Load Balancer, WAS로 접근한다.
- 데이터 처리: WAS가 필요한 데이터를 Cloud DB for MySQL에서 조회하거나 저장한다.
- 인증: Keycloak 기반 Issuer Server가 로그인과 토큰 발급을 담당한다.
- 콘텐츠 제공: Object Storage에 저장한 강의 콘텐츠를 CDN으로 제공한다.
- 운영과 배포: Bastion Host·SSL VPN으로 관리 경로를 구성하고, Private 서버의 외부 통신에는 NAT Gateway를 사용한다.
WEB, WAS, 인증 서버, DB는 Private 영역 중심으로 배치했다. 외부 진입점과 실제 서비스를 처리하는 서버를 나누고, 그 사이에 필요한 통신만 허용하는 것이 기본 방향이었다.
이 그림은 구성 요소와 관계를 보여주는 개요도이다. SSL VPN이나 세부 보안 정책까지 모두 표현한 배치도는 아니므로, 아래에서 실제로 구분해야 할 경로를 함께 설명한다.
## 1. 요구사항을 서버의 역할과 경계로 바꾸기
![](/notion-assets/ncp-lms-cloud-architecture/image-003.png)
요구사항 요약 1 — 개방형 구조, 클라우드 종속성 최소화, 향후 확장 방향.
첫 번째 요구사항은 개별 서버의 사양보다 아키텍처의 방향에 가까웠다. 특정 환경에 강하게 묶이지 않는 구조와 향후 하이브리드 환경으로의 확장을 고려해야 했다.
이번 프로젝트는 NCP에서 구현했지만, 애플리케이션과 인증, 데이터 저장의 역할을 구분하고 컨테이너 이미지로 배포할 수 있는 구조를 사용했다. 이후 다른 환경을 검토할 때도 무엇을 옮겨야 하는지 구분하기 쉬운 방향이다.
다만 Cloud DB, CDN 같은 관리형 서비스는 제공자의 설정과 기능에 의존한다. 컨테이너를 사용했다고 클라우드 종속성이 모두 사라지는 것은 아니다. G-Cloud 수준의 보안·안정성 충족 여부 역시 별도의 기준 검토가 필요한 항목으로 보았다.

이렇게 나누면 계층마다 허용할 통신과 확장 대상을 구분할 수 있다. WEB이 DB에 직접 연결될 필요가 없다면 그 경로를 열지 않고, WAS에서 필요한 DB 연결만 허용하는 식이다.
역할 분리는 장애가 발생했을 때 확인할 범위를 좁히는 데도 도움이 된다. 다만 계층 간 의존성은 남는다. WAS가 응답하지 않으면 WEB이 살아 있어도 강의 조회 같은 기능은 실패할 수 있다. 그래서 계층 분리와 함께 서버 이중화, 헬스체크, DB 장애 전환을 고려했다.
## 2. 사용자의 요청은 어디까지 가야 할까?
![](/notion-assets/ncp-lms-cloud-architecture/image-005.png)
요구사항 요약 3 — 고가용성, 부하 분산, 콘텐츠 전송 최적화.
서비스 요청의 기본 경로는 다음과 같이 잡았다.
**사용자 → L7 Load Balancer → WEB → L4 Load Balancer → WAS → Cloud DB**
외부에서 들어오는 웹 요청은 L7 Load Balancer가 받아 WEB 계층으로 분산한다. WEB은 요청에 따라 정적 파일을 제공하거나, 내부 L4 Load Balancer를 통해 WAS로 전달한다. WAS는 업무 로직을 처리하고 필요한 경우 DB에 접근한다.
예를 들어 사용자가 강의 목록을 조회한다고 가정해 보자.
1. 브라우저가 화면을 구성할 HTML, CSS, JavaScript 파일을 요청한다.
2. WEB 계층에서 받은 파일을 브라우저가 실행한다.
3. 화면에 강의 목록이 필요하면 브라우저가 API를 요청한다.
4. 해당 요청이 WEB과 내부 Load Balancer를 거쳐 WAS로 전달된다.
5. WAS가 DB에서 강의 정보를 조회하고 응답을 반환한다.
여기서 모든 요청이 DB까지 도달하는 것은 아니다. 정적 파일 요청은 WEB에서 처리할 수 있고, API도 처리 내용에 따라 DB 접근 여부가 달라진다. 강의 영상처럼 용량이 큰 콘텐츠에는 별도의 CDN 경로를 사용했다.
인증 기능은 Keycloak 기반 Issuer Server로 분리했다. 로그인과 토큰 발급을 인증 서버에 맡기고, WAS는 전달받은 인증 정보를 바탕으로 서비스 요청을 처리하는 역할을 갖도록 했다.
이때 아키텍처의 WEB → AUTH 화살표는 인증 연계 관계를 나타낸다. 실제 로그인 요청 순서는 사용하는 인증 흐름에 따라 달라진다. 예를 들어 브라우저를 인증 서버로 리디렉션하는 방식이라면 브라우저에서도 인증 엔드포인트에 접근할 수 있어야 한다. AUTH 서버 자체는 Private에 두더라도, 필요한 인증 경로를 외부에 제공하는 구성을 함께 고려해야 한다.
## 3. 서비스 접속과 관리자 접속을 나누기
![](/notion-assets/ncp-lms-cloud-architecture/image-006.png)
요구사항 요약 4 — 외부·내부 네트워크 분리, 공인 IP 최소화, 보안과 접근 제어.
사용자가 LMS에 접속하는 경로와 관리자가 서버에 접속하는 경로는 목적이 다르다. 따라서 두 경로를 따로 구성했다.
서비스 사용자는 Public 영역의 L7 Load Balancer로 들어오고, 운영자와 개발자는 Bastion Host 또는 SSL VPN을 이용하도록 했다. WEB, WAS, AUTH, DB에 각각 공인 IP를 붙여 외부 접속을 받는 대신, 필요한 진입점을 정하고 내부에서는 사설 IP로 통신하는 구조이다.
### Bastion Host와 SSL VPN의 역할
Bastion Host는 내부 서버로 접속하기 전에 거치는 관리용 서버이다.
**운영자·개발자 → Bastion Host → Private 서버**
관리 접속 경로를 모으고, Bastion의 접속 기록과 명령어 로그를 남겨 작업 이력을 추적할 수 있도록 구성했다.
SSL VPN은 외부 작업 환경에서 내부 사설망에 접근할 수 있는 경로로 사용했다. 접속 위치의 공인 IP가 달라지더라도 VPN 인증을 거친 사용자에게 내부 접근 경로를 제공하려는 목적이다.
VPN 접속만으로 내부 서버의 접근 제어가 없어지는 것은 아니다. NCP에서는 SSL VPN IP Pool에 대한 라우팅과 ACG(Access Control Group) 규칙을 함께 설정해야 한다. 필요한 관리 대상과 포트만 허용해야 한다는 원칙은 동일하다.
### 외부 LMS와의 연결
외부 LMS와 연계하는 상황은 별도 VPC를 두고 VPC Peering으로 연결하는 구조로 설계했다. 그림에서 허브 시스템과 외부 LMS가 서로 다른 VPC에 들어 있는 이유이다.
이 설계는 피어링 가능한 NCP VPC에 외부 LMS가 있다는 가정에 따른 것이다. 임의의 외부 기관이나 온프레미스 시스템까지 VPC Peering만으로 연결할 수 있다는 의미는 아니다.
NCP VPC Peering은 동일 리전 내에서 지원되며, 공식 가이드에서는 TCP처럼 양방향 통신이 필요한 경우 요청·수락 VPC를 바꾼 두 개의 피어링을 구성하도록 안내한다. 피어링 생성 후에는 상대 대역으로 향하는 Route Table과 접근 제어 규칙도 함께 맞춰야 한다.
## 4. 서버를 늘릴 수 있는 구조와 장애에 대비한 구조
![](/notion-assets/ncp-lms-cloud-architecture/image-007.png)
요구사항 요약 5 — 가상 서버 기반 구성, 인스턴스 증설, Load Balancer를 통한 분산.
WEB과 WAS는 각각 Auto Scaling Group으로 구성했다. WEB은 외부 L7 Load Balancer 뒤에, WAS는 내부 L4 Load Balancer 뒤에 배치했다.
계층별로 그룹을 나누면 어느 계층에서 부하가 발생하는지에 따라 확장 대상을 정할 수 있다. 예를 들어 API 처리에 부하가 집중된다면 WAS 계층의 확장을 검토할 수 있다.
Load Balancer는 여러 서버로 요청을 분산하고, Auto Scaling은 설정한 조건에 따라 서버 수를 조절한다. 두 기능이 함께 동작하려면 새 서버도 기존 서버와 같은 애플리케이션·설정으로 준비되고, 헬스체크를 통과한 뒤 요청을 받을 수 있어야 한다.
사용자의 세션이나 업로드 파일을 특정 서버의 로컬에만 보관하는지도 살펴야 한다. 다음 요청이 다른 서버로 가거나 기존 서버가 제거될 수 있기 때문이다. **서버 수를 늘리는 설정과, 서버가 바뀌어도 서비스가 동작하는 애플리케이션 구조를 함께 확인해야 한다.**
DB에는 Cloud DB for MySQL의 고가용성 구성을 사용했다. Primary 역할의 서버와 Standby 서버를 두어 장애 시 전환할 수 있는 구조이다. NCP 공식 문서에서는 이를 Master Server와 Standby Master Server로 설명한다.
그림에서 WAS가 DB 영역으로 연결된 것은 데이터 계층에 대한 의존 관계를 표현한 것이다. 일반 요청을 Primary와 Standby에 동시에 분산하거나, WAS가 백업 저장소에 직접 쿼리한다는 의미는 아니다.
고가용성 구성에도 장애 감지와 전환 시간은 존재한다. 운영 단계에서는 전환 중 실패한 요청을 어떻게 처리하고, 애플리케이션이 DB에 다시 연결하는지까지 함께 검증해야 한다.
## 5. 강의 콘텐츠는 데이터와 전달 경로를 함께 분리하기
![](/notion-assets/ncp-lms-cloud-architecture/image-008.png)
요구사항 요약 6 — 안정적인 데이터 저장, 스토리지 확장, 대용량 콘텐츠 제공.
LMS에서는 회원·강의 정보처럼 조회와 갱신이 필요한 데이터와, 영상·문서 같은 콘텐츠를 구분할 필요가 있다.
회원이나 강의 메타데이터는 DB에서 관리하고, 대용량 강의 콘텐츠는 Object Storage에 저장해 CDN으로 제공하도록 구성했다. Block Storage와 Object Storage 역시 사용 목적을 나누어 보았다. 전자는 서버에 연결해 사용하는 디스크이고, 후자는 파일을 객체 단위로 저장하고 접근하는 서비스이다.
콘텐츠 요청 경로는 다음과 같다.
**사용자 → CDN → 필요 시 Object Storage**
CDN에 유효한 캐시가 있으면 캐시된 콘텐츠로 응답하고, 원본이 필요하면 Object Storage에서 가져온다. 모든 영상 요청을 WEB/WAS가 직접 처리하는 부담을 줄이려는 설계이다.
다만 CDN을 연결하는 것만으로 콘텐츠의 접근 권한까지 해결되지는 않는다. 수강 권한이 필요한 강의라면 콘텐츠 URL을 받은 사용자가 누구인지, 원본 저장소에 직접 접근할 수 있는지, 권한이 없는 사용자의 요청을 어떻게 제한할지를 별도로 설계해야 한다.
요구사항에 적힌 다운로드·스트리밍 제어와 대규모 전송 성능은 이런 정책 및 성능 검증까지 포함하는 주제이다. 이번 실습에서는 Object Storage와 CDN으로 제공 경로를 분리한 구성에 초점을 맞췄다.
## 6. Private 서버는 배포 이미지를 어떻게 가져올까?
서비스 서버를 Private에 두어도 패키지 설치, 외부 API 호출, 컨테이너 이미지 다운로드를 위한 외부 통신은 필요하다. 이 경로에 NAT Gateway를 사용했다.
CI/CD는 GitHub Actions와 GHCR(GitHub Container Registry)을 기반으로 구성했다. 이때 **이미지를 만드는 순서와 네트워크 연결을 시작하는 방향**을 나누어 보면 이해하기 쉽다.
이미지 빌드·등록 흐름은 다음과 같다.
**소스 변경 → GitHub Actions에서 이미지 빌드 → GHCR에 이미지 등록**
반면 Private 서버가 이미지를 내려받을 때 연결을 시작하는 방향은 다음과 같다.
**Private 서버 → NAT Gateway → GHCR**
이미지 데이터는 서버가 시작한 연결의 응답으로 돌아온다. GHCR이 NAT Gateway를 통과해 내부 서버로 새로운 접속을 시작하는 구조로 이해하면 안 된다.
NCP의 공인 NAT Gateway는 인터넷 아웃바운드 통신에 할당된 공인 IP를 사용한다. 서버 측 Route Table에도 외부 목적지로 향하는 경로를 설정해야 한다. 고정 IP 기반으로 외부 API 접근을 허용해야 하는 경우에는 상대 시스템이 보게 될 출발지 IP도 이 경로를 기준으로 확인할 수 있다.
NAT Gateway는 서버의 외부 통신 경로를 제공한다. 새 버전의 배포를 언제 시작할지, 컨테이너를 어떻게 교체할지, 실패했을 때 어떤 버전으로 되돌릴지는 별도의 배포 절차에 속한다. 네트워크 경로와 배포 자동화의 역할을 구분하는 것이 중요했다.
## 7. 보안 구성과 운영 기록까지 연결하기
보안 요구사항에는 네트워크 분리뿐 아니라 방화벽, IPS, DDoS 대응, WAF 같은 항목이 포함되어 있었다.
이번 프로젝트에서는 IPS·IDS 기반 보안 구성과 Cloud Log Analytics를 활용한 로그 수집을 진행했다. Bastion의 접속·명령어 기록도 운영 접근을 확인하기 위한 자료로 남기도록 구성했다.
IDS는 이상 징후나 공격을 탐지하는 역할이고, IPS는 정책에 따라 공격 트래픽을 차단하는 역할까지 수행한다. WAF는 웹 요청을 대상으로 한 공격 대응에 초점을 둔다. 각각 살펴보는 대상과 동작이 다르므로 적용 위치와 정책을 구분해야 한다.
아키텍처에는 메일 발송을 위한 Cloud Outbound Mailer도 함께 포함했다. 사용자 요청을 처리하는 WEB/WAS 외에도 콘텐츠, 인증, 메일, 로그 같은 기능이 있어야 서비스 운영의 전체 흐름을 설명할 수 있기 때문이다.
보안 장비의 구성 이후에는 정책이 실제 트래픽에 어떻게 적용되는지도 확인해야 한다. 어떤 이벤트를 수집하고, 차단으로 인한 서비스 영향은 없는지, 문제가 생겼을 때 어느 로그를 확인할지를 함께 정리해야 운영으로 이어질 수 있다.
## 설계하고 나서 남은 기준
이번 프로젝트에서는 요구사항 분석부터 시연용 LMS 개발, 네트워크 구성, 서버 역할 분리, 배포 자동화까지 전체 흐름을 직접 연결해 볼 수 있었다.
그 과정에서 리소스 하나를 추가할 때마다 함께 정해야 할 내용이 있다는 점을 배웠다. 서버를 Private에 두면 관리와 배포 경로가 필요하고, 서버를 여러 대로 늘리면 세션과 파일의 위치를 확인해야 한다. 콘텐츠를 CDN으로 분리하면 캐시와 접근 권한도 함께 생각해야 한다.
이후 아키텍처를 볼 때는 다음 질문을 기준으로 삼으려고 한다.
- 이 요청은 어디에서 시작하고, 어느 구성 요소까지 도달해야 하는가?
- 그 경로에 필요한 접근 권한만 허용되어 있는가?
- 트래픽이 늘어나면 어느 계층을 확장해야 하는가?
- 서버나 DB가 바뀌는 동안 사용자의 요청은 어떻게 처리되는가?
다음 검증 과제도 여기에서 이어진다. 새로 늘어난 서버가 같은 버전으로 준비되는지, DB 전환 후 애플리케이션이 재연결하는지, 콘텐츠 권한이 유지되는지 확인하는 것이다. 설계도에 그린 경로를 실제 요청과 장애 상황으로 확인할 수 있어야, 그 구성이 왜 필요한지도 더 구체적으로 설명할 수 있다.
