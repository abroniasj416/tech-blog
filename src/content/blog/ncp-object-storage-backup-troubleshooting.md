고객사 서버에서 매일 비슷한 시간대에 CPU 사용률이 95% 이상으로 치솟고, 서버가 응답하지 않는 Hang 현상이 반복됐다.
처음에는 서버 리소스가 부족한 상황처럼 보였다. 그런데 디스크 상태와 백업 스크립트를 함께 확인하면서 다른 단서를 발견했다. 로컬 백업 디렉터리로 사용하던 경로가 실제로는 Object Storage를 마운트한 경로였던 것이다.
이번 글은 그 경로를 어떻게 사용하고 있는지 추적하고, 백업을 API 호출 방식으로 바꾸어 반복 장애를 해결한 과정이다.
## 1. `df -h`에서 발견한 낯선 용량
서버에 접속해 먼저 디스크 상태를 확인했다.
```bash
df -h
```
특정 파일 시스템의 사용 가능한 용량이 페타바이트 단위로 표시되고 있었다. 서버에 연결된 일반적인 로컬 디스크라고 보기에는 낯선 수치였다. 경로를 확인해 보니 Object Storage가 마운트되어 있었고, 고객사는 이 마운트 지점을 백업 디렉터리로 사용하고 있었다.
여기서 주의할 점이 있다. `df -h`에 매우 큰 용량이 표시됐다고 해서 실제로 그만큼의 디스크를 할당받았거나, 그 공간에 데이터가 가득 차 있다는 뜻은 아니다. 마운트된 파일 시스템이 보고하는 용량 값과 실제 객체 저장량을 구분해야 한다.
이 수치는 장애 원인 자체가 아니라, **백업 경로 뒤에 어떤 스토리지가 연결되어 있는지 확인하게 된 단서**였다.
기존 구조는 다음과 같았다. 서버에서는 일반 디렉터리처럼 접근하지만, 실제 백업 데이터는 마운트 계층을 거쳐 Object Storage에 저장되고 있었다.
![기존 구조: 서버에 Object Storage(S3)를 mount한 뒤, mount point를 백업 디렉토리로 사용](/notion-assets/ncp-object-storage-backup-troubleshooting/image-001.png)
그림의 EC2·S3 아이콘은 서버와 Object Storage의 연결 방식을 설명하기 위한 것이다. 이 사례에서 사용한 환경은 Rocky Linux와 NAVER Cloud Platform Object Storage이다.
## 2. 백업 스크립트가 실제로 접근하던 곳
당시 백업 스크립트의 핵심 부분은 다음과 같다.
```bash
tar zcvf ${ZIP_DIR}/httpd_${BACKUP_DATE}.tar.gz -X ${ZIP_DIR}/httpd-exclude.lst ${HTTPD_DIR}
cp ${ZIP_DIR}/httpd_${BACKUP_DATE}.tar.gz ${BACKUP_DIR}/httpd_${BACKUP_DATE}.tar.gz

rm -f ${ZIP_DIR}/httpd_${BACKUP_DATE}.tar.gz

find ${BACKUP_DIR}/ -mtime +7 -exec rm -f {} \;
```
작업 흐름을 풀어보면 어렵지 않다.
1. `${HTTPD_DIR}`를 압축해 로컬 작업 경로인 `${ZIP_DIR}`에 백업 파일을 만든다. `-X`로 지정한 목록의 항목은 압축 대상에서 제외한다.
2. 압축 파일을 `${BACKUP_DIR}`로 복사한다.
3. 로컬 작업 경로에 남은 압축 파일을 삭제한다.
4. 백업 경로를 순회하며 수정 시각이 `-mtime +7` 조건에 해당하는 항목에 삭제 명령을 실행한다.
문제는 `${BACKUP_DIR}`가 로컬 디스크의 디렉터리가 아니라는 점이었다. 스크립트에 적힌 명령은 익숙한 `cp`와 `find`였지만, 두 명령 모두 Object Storage 마운트 경로를 대상으로 동작하고 있었다.
특히 오래된 백업을 정리하는 마지막 줄에 주목했다. 삭제 대상을 고르려면 먼저 하위 경로를 순회하고 각 항목의 수정 시각을 확인해야 하기 때문이다.
참고로 GNU `find`의 `-mtime +7`은 단순히 “7일을 조금 넘긴 파일”이라는 뜻이 아니다. 수정 후 경과 시간을 24시간 단위로 계산하고 소수 부분을 버린 값이 7보다 커야 하므로, 기본 동작에서는 **수정 후 최소 8일이 지난 항목**이 대상이다. 또한 기존 명령에는 `-type f`가 없어 일반 파일만 검색하도록 제한되어 있지 않았다.
## 3. 로컬 디렉터리처럼 보여도 조회 비용은 달랐다
Object Storage는 버킷 안의 객체를 키로 식별하고 API로 접근하는 스토리지다. 마운트 도구를 사용하면 파일과 디렉터리처럼 다룰 수 있지만, 그 아래의 동작까지 로컬 파일 시스템과 같아지는 것은 아니다.
마운트 도구의 구현과 캐시 상태에 따라 디렉터리 순회나 속성 확인이 원격 목록 조회와 메타데이터 요청으로 이어질 수 있다. 예를 들어 S3 호환 스토리지를 마운트하는 도구인 s3fs도 공식 문서에서 디렉터리 목록 조회 같은 메타데이터 작업이 네트워크 지연의 영향을 받는다고 설명한다. 이는 동작을 이해하기 위한 예시이며, 당시 사용한 마운트 도구를 s3fs로 특정한 것은 아니다.
따라서 확인해야 할 것은 스토리지의 표시 용량보다 **실제로 순회하는 항목 수와 조회 방식**이었다. `find`가 비어 있는 저장 공간까지 읽거나, 용량이 크다는 이유만으로 무한히 탐색하는 것은 아니다.
이번에는 CPU가 급등하는 시간대와 백업 실행 흐름을 비교하고, 마운트 경로를 반복 조회하는 정리 작업을 주요 원인 후보로 판단했다. 다만 원격 조회에 지연이 생긴다는 사실만으로 CPU 사용률 95%를 직접 설명할 수는 없다. 압축 작업, 마운트 프로세스, 조회·삭제 처리 등 각 단계의 영향을 구분해서 봐야 한다.
당시 확인한 내용으로는 `find` 한 줄의 영향만 분리해 확정하기보다, 마운트 경로에 복사와 전체 순회를 맡긴 백업 구조를 개선하는 방향이 적절하다고 판단했다.
## 4. 마운트 경로를 거치지 않는 백업으로 변경
백업 파일을 로컬에서 생성한 뒤, Object Storage API를 호출해 직접 업로드하도록 수정했다. 백업 저장 경로의 마운트 의존을 제거하고, 오래된 백업을 정리하던 `find` 명령도 백업 스크립트에서 제거했다.
변경 후 구조는 다음과 같다.
![개선 구조: mount 의존을 제거하고, 서버에서 Object Storage API를 직접 호출하여 백업 데이터 저장](/notion-assets/ncp-object-storage-backup-troubleshooting/image-002.png)
두 번째 그림 역시 같은 구성을 AWS 아이콘으로 표현한 것이다. 핵심은 스크립트가 마운트된 디렉터리에 파일을 복사하는 대신, 객체 업로드 작업을 명시적으로 수행하게 됐다는 점이다.
마운트 도구도 내부적으로는 API를 사용할 수 있다. 따라서 이번 변경의 의미는 API를 처음 사용하게 됐다는 데 있지 않다. **마운트 계층을 거치던 파일 작업을 직접 제어하는 업로드 작업으로 바꿨다**는 데 있다.
NCP Object Storage는 S3 호환 CLI도 제공한다. 직접 API 요청을 구현하거나, SDK·CLI를 통해 객체를 업로드하는 방식으로 백업 흐름을 구성할 수 있다. 이 글에서는 실제 변경에 사용한 인증 정보와 전체 업로드 구현은 생략한다.
### 오래된 백업을 지우는 작업은 별도로 설계한다
`find`를 제거했다고 보관 기간 관리까지 없어져도 되는 것은 아니다. 오래된 백업 정리는 Object Storage의 수명 주기 정책이나 API 기반 삭제 작업으로 분리하는 편이 적합하다고 판단했다.
수명 주기 정책은 객체의 저장 기간과 접두어 등을 기준으로 삭제 대상을 관리할 수 있다. 다만 기존 `find`의 파일 수정 시각 기준과 객체가 저장된 시점 기준은 다를 수 있어, 기존 보관 조건을 그대로 옮겼다고 생각해서는 안 된다. 사용 중인 서비스·리전·버킷 설정에서 정책을 지원하는지도 확인해야 한다.
당시 작업 범위는 API 기반 업로드로의 전환과 `find` 제거였다. 수명 주기 정책과 API 기반 정리는 보관 방식을 별도로 설계할 때 검토할 수 있는 선택지다.
백업 흐름을 다시 구성할 때는 업로드 성공을 확인한 뒤 로컬 파일을 정리하도록 해야 한다. 서버가 멈추지 않는 것과 복구 가능한 백업이 남는 것은 별개의 확인 항목이기 때문이다.
## 5. 변경 후 반복 장애가 해소됐다
구조를 변경한 뒤, 특정 시간대마다 반복되던 CPU 급등과 서버 Hang 현상이 해소됐다. 백업 작업도 마운트 상태에 의존하지 않고 객체 업로드 단계로 분리됐다.
다만 이번에는 업로드 방식 변경과 `find` 제거를 함께 적용했다. 따라서 두 변경 중 어느 쪽이 얼마만큼 기여했는지까지 나누어 설명할 수는 없다. 반복 장애가 해소된 결과만으로 `find`가 단독 원인이었다고 확정하거나, CPU 개선 폭을 수치로 제시할 수는 없다.
## 6. 경로 뒤에 연결된 스토리지까지 확인하기
이번 장애 대응은 서버 접속부터 디스크 상태 확인, 백업 스크립트 분석, 접근 방식 변경까지 단독으로 진행했다. 그 과정에서 같은 경로 표기와 같은 명령어라도, 대상 스토리지에 따라 동작 비용이 달라질 수 있다는 점을 배웠다.
Object Storage를 마운트하는 방식이 모든 환경에서 잘못된 선택이라는 뜻은 아니다. 필요한 파일 시스템 기능과 실제 접근 패턴에 맞는지 판단해야 한다. 이번처럼 백업 파일을 생성해 저장하고 보관 기간에 따라 정리하는 작업에서는, 객체 업로드와 보관 정책을 명시적으로 나누는 방식이 더 적합했다.
특정 시간대에만 장애가 반복된다면 자원 사용률과 함께 그 시간에 실행되는 작업을 살펴볼 필요가 있다. 그리고 스크립트의 경로를 볼 때는 이름에서 멈추지 않고, 그 뒤에 로컬 디스크가 있는지, 원격 파일 시스템이 있는지, Object Storage가 있는지까지 확인해야 한다.
