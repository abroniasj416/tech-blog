## 여행 계획을 한곳에서 함께 바꿀 수 있다면
친구들과 여행을 준비할 때 지도 링크는 단체 채팅방에, 일정은 메모장에, 비용은 스프레드시트에 흩어지기 쉽다. 장소 하나를 추가해도 누군가가 다시 정리해야 하고, 대화가 쌓이면 최종적으로 어디에 가기로 했는지 찾기 어려워진다.
COTRIP은 이런 정보 분산 문제에서 출발한 여행 계획 협업 서비스이다. 하나의 여행 페이지에서 장소를 추가하고, 방문 순서를 바꾸고, 메모를 함께 작성할 수 있도록 기획했다.
![여행 계획 과정에서 정보가 흩어지고 협업이 어려워지는 실제 사용자 불편 사례](/notion-assets/ncp-websocket-redis-pubsub/image-001.png)
기획 과정에서 참고한 여행 계획 협업의 불편 사례이다. 채팅방과 스프레드시트에 정보가 흩어지고, 참여자들이 같은 계획을 확인하기 어렵다는 문제가 담겨 있다.
개인 프로젝트로 React 기반 프런트엔드와 Java Spring Boot 기반 백엔드를 구현하고, NCP에 인프라를 구성했다. 그 과정에서 가장 중요하게 다룬 질문은 다음과 같았다.
**같은 여행 페이지를 보고 있는 사용자들이 서로 다른 WAS에 연결되어 있다면, 한 사람이 수정한 내용을 어떻게 다른 사람에게 전달할까?**
이 글에서는 이 문제를 중심으로 WebSocket과 Redis Pub/Sub을 연결한 이유, PostgreSQL과 Redis의 역할, 그리고 이를 지원하는 클라우드 인프라를 정리한다.
## WebSocket 연결은 각 WAS에 나뉘어 있다
실시간 협업에서는 한 사용자가 장소를 추가했을 때 다른 참여자의 화면에도 변경 사항이 전달되어야 한다. 이를 위해 클라이언트와 서버가 연결을 유지하면서 양방향으로 메시지를 주고받는 WebSocket을 사용했다.
WAS가 한 대라면 해당 서버가 자신에게 연결된 사용자들을 관리하면서 필요한 메시지를 전달할 수 있다. 그런데 가용성과 확장성을 고려해 WAS를 여러 대로 구성하면 연결도 여러 서버로 나뉜다.
예를 들어 같은 여행 계획에 참여한 두 사용자가 다음과 같이 연결되어 있다고 가정해 보자.
- User 1은 WAS 1에 WebSocket으로 연결되어 있다.
- User 2는 WAS 4에 WebSocket으로 연결되어 있다.
User 1이 장소를 추가하면 먼저 WAS 1이 변경 요청을 받는다. WAS 1은 자신의 연결 목록에서 User 2를 찾을 수 없다. User 2와 연결을 유지하는 서버는 WAS 4이기 때문이다.
Load Balancer가 새로운 연결을 여러 WAS로 분산하더라도, 각 WAS의 메모리에 있는 연결 정보와 변경 이벤트까지 자동으로 공유해 주지는 않는다. WAS 4가 User 2에게 변경 사항을 보내려면, **WAS 1에서 발생한 이벤트를 WAS 4도 알 수 있는 경로**가 필요하다.
## Redis Pub/Sub으로 WAS 사이에 이벤트 전달하기
이 경로에 Redis Pub/Sub을 사용했다. Pub/Sub은 Publish와 Subscribe의 줄임말이다. 발행자는 특정 채널에 메시지를 보내고, 그 채널을 구독한 수신자들이 메시지를 받는다.
COTRIP에서는 WAS들이 Redis 채널을 구독하고, 변경을 처리한 WAS가 해당 채널에 이벤트를 발행하도록 구성했다.
![N중화된 WAS 환경에서 Redis Pub/Sub을 활용한 실시간 이벤트 브로드캐스트 구조](/notion-assets/ncp-websocket-redis-pubsub/image-002.png)
WAS 1에서 발생한 변경 이벤트가 Redis를 거쳐 다른 WAS에 전달되고, WAS 4가 자신에게 연결된 User 2에게 WebSocket으로 알리는 흐름이다. 그림의 Subscribe 화살표는 미리 구독한 WAS들이 이벤트를 수신하는 관계를 나타낸다.
이 구조에서 WebSocket과 Redis Pub/Sub은 서로 다른 구간을 담당한다.

Redis는 이벤트를 전달하는 중간 계층이고, 브라우저에 최종 메시지를 보내는 주체는 각 WAS이다. Redis에 WebSocket 연결 자체를 옮기거나, 다른 WAS의 연결을 직접 사용하는 방식은 아니다.
따라서 WAS가 늘어나도 새 서버가 필요한 채널을 구독하고 자신의 WebSocket 연결을 관리하면 같은 이벤트 전달 구조에 참여할 수 있다.
## 장소 하나를 추가했을 때의 전체 흐름
장소 추가를 예로 들면 처리 흐름은 다음과 같다.
1. User 1이 여행 페이지에서 장소를 추가한다.
2. User 1과 연결된 WAS 1이 변경 요청을 처리한다.
3. 여행 계획의 변경 데이터를 PostgreSQL에 저장한다.
4. WAS 1이 Redis 채널에 변경 이벤트를 발행한다.
5. 해당 채널을 구독한 WAS들이 이벤트를 받는다.
6. 각 WAS가 자신에게 연결된 해당 여행 계획의 참여자에게 WebSocket 메시지를 전달한다.
7. 클라이언트가 전달받은 내용을 화면에 반영한다.
여기서 “모든 사용자에게 전달한다”의 범위는 **같은 여행 계획에 참여하는 사용자**이다. 다른 여행의 참여자에게까지 이벤트가 전달되어서는 안 된다.
따라서 애플리케이션에서는 어떤 여행 계획의 이벤트인지 구분하고, 수신 대상이 그 여행의 참여자인지 확인해야 한다. Redis 채널을 구독하는 서버의 범위와 브라우저로 메시지를 보낼 사용자의 범위를 구분하는 것이 중요하다.
![**WebSocket 기반 실시간 협업이 필요한 서비스 화면** \| 장소 추가, 순서 변경, 메모 수정 이벤트를 여러 WAS 서버에 동기화해야 하는 구조](/notion-assets/ncp-websocket-redis-pubsub/image-003.png)
COTRIP의 여행 계획 화면이다. 지도와 장소 목록을 함께 보여주고, 장소 추가·순서 변경·메모 수정처럼 참여자들이 함께 확인해야 하는 변경을 다룬다.
화면에서 보면 장소 목록 하나가 바뀌는 동작이지만, 서버에서는 데이터 저장과 서버 간 이벤트 전달, 연결된 참여자에게 보내는 작업이 이어진다.
## PostgreSQL과 Redis에 서로 다른 역할 맡기기

Redis는 캐시 용도로도 많이 사용되지만, 이 프로젝트에서 설명하는 역할은 Pub/Sub을 통한 이벤트 전달이다. “저장된 여행 계획을 다시 읽는 것”과 “지금 접속한 사람에게 변경을 알리는 것”을 각각의 목적에 맞게 나눈 셈이다.
다만 데이터 저장과 이벤트 발행은 별개의 작업이다. 예를 들어 DB 저장은 성공했는데 Redis에 이벤트를 발행하기 전에 WAS가 종료될 수 있다. 반대로 DB의 변경이 확정되기 전에 이벤트를 보내면 다른 사용자가 아직 저장되지 않은 상태를 전달받을 수도 있다.
그래서 저장 완료를 기준으로 알림을 보내는 순서와, 그 사이에 실패했을 때의 처리를 함께 고려해야 한다. 이벤트 전파 구조를 마련했다고 두 작업이 하나의 트랜잭션이 되는 것은 아니다.
## Pub/Sub의 한계와 이후 보완할 부분
Redis Pub/Sub을 사용하면 연결된 WAS들 사이에 이벤트를 전파할 수 있다. 다만 이것이 모든 상황에서 메시지 수신을 보장한다는 뜻은 아니다.
[Redis 공식 문서](https://redis.io/docs/latest/develop/pubsub/)에서는 Pub/Sub의 전달 방식을 **at-most-once**로 설명한다. 구독자가 연결을 잃었거나 메시지를 처리하지 못하면 해당 메시지는 나중에 자동으로 다시 전달되지 않는다.
예를 들어 WAS 4의 Redis 연결이 끊겨 있는 동안 장소 추가 이벤트가 발행되었다면, 연결이 복구되어도 그 이벤트가 자동 재생되지는 않는다. 브라우저의 WebSocket 연결이 끊긴 상황도 별도로 처리해야 한다.
이 특성을 기준으로 다음과 같은 보완 방향을 생각할 수 있다.
- 재접속하면 PostgreSQL에 저장된 최신 여행 계획을 다시 조회한다.
- 계획의 버전이나 이벤트 식별자를 활용해 오래된 변경과 중복 반영을 구분한다.
- 중단 중 발생한 이벤트까지 처리해야 한다면 메시지 보관·재처리를 지원하는 방식을 검토한다.
- DB 변경과 발행 요청을 함께 기록한 뒤 전달하는 방식으로, 저장 후 이벤트 발행이 실패하는 상황에 대비한다.
이 항목들은 이번 글에서 구현을 완료했다고 소개하는 기능이 아니라, 현재 구조를 보완하기 위한 과제이다.
동시 수정도 따로 다뤄야 한다. 두 사용자가 같은 장소의 순서를 동시에 바꾸면 어느 요청을 반영할지 결정해야 한다. Pub/Sub은 변경 사실을 전달하는 역할을 하므로, 수정 충돌을 처리하는 규칙은 애플리케이션과 DB에서 정해야 한다.
## 이 구조를 NCP 인프라에 배치하기
![NCP 기반 COTRIP 서비스 인프라 아키텍처](/notion-assets/ncp-websocket-redis-pubsub/image-004.png)
전체 인프라는 WEB / WAS / DB를 분리한 3-Tier 구조로 구성했다. 여기에 실시간 이벤트를 전달할 Redis와 운영·배포를 위한 경로를 더했다.
### 사용자 요청과 내부 통신
사용자 요청의 기본 경로는 다음과 같다.
**사용자 → L7 Load Balancer → WEB → 내부 L4 Load Balancer → WAS**
WEB은 정적 리소스 제공과 요청 전달을 담당하고, 업무 로직이 필요한 요청은 WAS로 전달한다. 모든 요청이 DB까지 가는 것은 아니며, WAS가 필요한 데이터 작업을 PostgreSQL에서 처리한다.
WebSocket도 중간의 Load Balancer와 WEB 계층을 통과해 WAS까지 연결되어야 한다. 일반 페이지가 열린다는 것만으로 WebSocket 경로까지 확인된 것은 아니다. 중간 프록시의 WebSocket 전달 설정과 유휴 연결 종료 시간을 함께 확인해야 한다.
WEB, WAS, PostgreSQL, Redis는 Private 영역 중심으로 배치했다. 외부 사용자는 서비스 진입점을 통해 접근하고, PostgreSQL과 Redis에 직접 연결하지 않도록 했다.
아키텍처의 PostgreSQL Primary/Standby 표시는 고가용성 구성을 나타낸다. 일반 쓰기 요청을 두 서버에 동시에 분산한다는 의미는 아니다.
### Auto Scaling과 오래 유지되는 연결
WEB과 WAS는 여러 대로 확장할 수 있도록 설계했다. Redis Pub/Sub은 서버가 나뉘어도 변경 이벤트를 전달하기 위한 구성이다.
WebSocket처럼 오래 유지되는 연결에서는 서버 수만큼 연결이 즉시 재배치되지는 않는다. 새 WAS가 추가되어도 기존 연결은 원래 서버에 남고, 이후의 새 연결이나 재접속이 분산된다.
반대로 서버를 줄이거나 배포를 위해 종료하면 해당 서버가 유지하던 연결은 끊길 수 있다. 그래서 확장 정책을 정할 때 연결 수와 자원 사용량을 함께 보고, 종료 과정의 연결 처리와 클라이언트 재접속을 검토해야 한다. Pub/Sub 연결이 준비된 뒤 새 WAS가 사용자 연결을 받는지도 확인할 대상이다.
## 관리·배포 경로와 운영 데이터도 분리하기
실시간 이벤트 경로와 함께 운영자가 접근하는 경로, 새 버전을 배포하는 경로, 로그와 백업도 구성했다.
### 관리자와 DB 접근
서버 관리에는 Bastion Server와 SSL VPN을 이용하는 경로를 두었다. 사용자가 웹 서비스에 접속하는 경로와 개발자가 내부 서버를 관리하는 경로를 나누기 위해서이다.
DB 관리 접근에는 별도의 접근 제어 경로를 설계했다. 애플리케이션의 DB 연결과 운영자의 관리 접속은 필요한 계정과 권한이 다르므로 각각 제한해야 한다.
### 이미지 배포와 외부 API
배포에는 GitHub Actions와 GHCR(GitHub Container Registry)을 사용했다. GitHub에 코드를 Push하면 Actions가 빌드와 이미지 생성 작업을 수행하고, 이미지를 GHCR에 등록한다.
Private 서버가 이미지를 가져올 때는 다음 방향으로 연결한다.
**Private 서버 → NAT Gateway → GHCR**
서버가 시작한 연결의 응답으로 이미지를 내려받는 구조이다. NAT Gateway는 이 외부 통신 경로를 제공하고, 이미지 교체 시점과 컨테이너 실행은 배포 절차에서 처리한다.
장소 검색과 지도 기능에는 Naver Search API와 Maps 서비스를 연동했다. 서버에서 수행하는 외부 API 호출은 NAT Gateway를 통한 아웃바운드 경로를 사용하도록 설계했다. 브라우저에서 이루어지는 지도 리소스 요청과 서버의 API 호출은 요청 주체를 구분해서 봐야 한다.
### 로그·백업과 비밀정보
WAS 로그는 Cloud Log Analytics로 수집하도록 구성했다. 협업 화면의 변경이 전달되지 않을 때 요청 처리, 이벤트 발행, 수신 후 전달 중 어느 단계에서 문제가 발생했는지 확인할 근거가 필요하기 때문이다.
백업은 WAS 로그와 DB 데이터의 복구를 고려해 계획했다. 설계 당시 주 1회 전체 백업과 매일 증분 백업을 검토했으며, 이는 계획한 정책이다. 실제 적용은 서버 파일 백업과 Cloud DB 자체 백업의 지원 방식에 맞춰 구분해야 한다.
Cloud DB for PostgreSQL에는 별도의 백업·시점 복원 기능이 있다. 백업 주기와 보관 기간을 정한 뒤 실제 복원이 되는지 확인해야 한다. DB 이중화는 서버 장애에 대비하고, 백업은 삭제나 잘못된 변경 등으로부터 데이터를 복구하는 데 사용한다.
DB 접속 정보와 API Key처럼 민감한 값은 코드와 분리해 관리하기 위해 Secret Manager를 사용했다. IDS·IPS 기반 보안 구성도 함께 고려했다.
## 연결을 분산한 다음에는 이벤트가 흐르는 길이 필요했다
COTRIP을 만들면서 실시간 협업이라는 서비스 특성이 인프라 설계에 직접 영향을 준다는 점을 경험했다.
WAS를 여러 대로 구성하니 각 서버가 유지하는 WebSocket 연결도 나뉘었다. 이를 연결하기 위해 Redis Pub/Sub으로 서버 사이에 변경 이벤트가 흐르는 경로를 만들고, 각 WAS가 자신의 연결을 통해 참여자에게 전달하도록 했다.
여기에서 얻은 기준은 데이터의 원본, 변경을 알리는 수단, 현재 사용자의 연결을 각각 구분해서 보는 것이다. COTRIP에서는 그 역할을 PostgreSQL, Redis Pub/Sub, WAS의 WebSocket 연결에 나누어 맡겼다.
다음으로 검증하고 싶은 부분도 명확해졌다. 서버가 추가되거나 종료될 때, Redis 연결이 잠시 끊길 때, 사용자가 다시 접속할 때 화면이 최신 데이터로 돌아오는지 확인하는 것이다. 실시간 협업의 완성도를 높이려면 연결이 정상일 때의 전달 흐름에 더해, 연결이 끊긴 뒤 상태를 맞추는 과정까지 이어져야 한다.
