## 들어가며
dnf가 받아 온 메타데이터는 저장소마다 따로 `/var/cache/dnf/` 아래에 저장된다. 검색할 때만 메모리에서 하나로 합친다.
이전 편 **\[dnf install은 어떻게 패키지를 찾는가\]**에서 정리한 내용을 짧게 되짚으면 이렇다. `dnf install nginx`를 실행하면 dnf는 다음 순서로 움직인다.
1. 사용 중인 모든 저장소에서 메타데이터(패키지 목록)를 받는다.
2. 받은 목록을 합쳐서 nginx와 의존성(nginx가 동작하는 데 필요한 다른 패키지)을 찾는다.
3. 후보가 여러 개면 정해진 규칙으로 하나를 고른다.
4. 저장소 주소와 패키지의 위치를 합쳐 rpm 파일을 받고 설치한다.
이번 글은 1번 단계를 더 자세히 들여다본다. 질문은 두 가지다.
- 메타데이터의 시작점인 repomd.xml은 누가 만드는가?
- 받아 온 메타데이터는 내 서버의 어디에, 어떤 모양으로 저장되는가?
용어가 낯설다면 이전 편 **\[dnf install은 어떻게 패키지를 찾는가\]**의 "먼저 알아둘 용어" 부분을 먼저 읽고 오는 것을 권한다. 이 글에서 다시 등장하는 용어는 그때그때 짧게 설명한다.
## repomd.xml은 저장소 서버에 있는 파일이다
repomd.xml은 dnf가 만드는 파일이 아니다. 저장소를 운영하는 쪽이 미리 만들어 서버에 올려 둔 파일이고, dnf는 그것을 읽어 올 뿐이다.
처음에는 이렇게 오해하기 쉽다. "내가 `/etc/yum.repos.d/`에 .repo 파일을 만들면, dnf가 그 안의 주소(baseurl)를 repomd.xml에 기록하는구나." 실제로는 방향이 반대다.

도서관에 비유하면 .repo 파일은 내 수첩에 적어 둔 도서관 주소이고, repomd.xml은 도서관 입구에 붙어 있는 안내도다. 수첩에 주소를 적는다고 도서관에 안내도가 생기지는 않는다.
저장소 운영자는 `createrepo_c`라는 도구로 repomd.xml과 나머지 메타데이터를 만든다. 이 도구는 디렉터리 안의 rpm 파일을 하나씩 열어 이름, 버전, 의존성 같은 정보를 읽고 `repodata/` 디렉터리를 생성한다. 직접 저장소를 만드는 방법은 시리즈의 뒤쪽 글에서 다룬다.
그래서 .repo 파일에 적은 주소에 `repodata/repomd.xml`이 없으면 dnf는 다음과 같은 오류를 낸다.
```plain text
Errors during downloading metadata for repository 'soojin':
  - Status code: 404 for http://repo.example.com/soojin/repodata/repomd.xml
```
404는 웹 서버가 "요청한 파일이 없다"고 답할 때 쓰는 번호다.
## dnf가 메타데이터를 받아오는 순서
dnf는 저장소마다 repomd.xml을 먼저 받고, 거기에 적힌 파일을 이어서 받는다. 이 과정을 사용 중인(enabled=1) 저장소 수만큼 반복한다.
저장소 하나에서 일어나는 일을 순서대로 적으면 다음과 같다.
1. .repo 파일에서 저장소 주소(baseurl)를 읽는다. 주소 대신 mirrorlist가 적혀 있으면 먼저 미러 목록을 받아 그중 하나를 고른다. 미러는 원본 저장소와 같은 내용을 복제해 둔 다른 서버다.
2. `주소/repodata/repomd.xml`을 요청한다. 이름이 항상 고정되어 있어서 dnf가 처음 찾아가는 출발점이 된다.
3. repomd.xml에 적힌 목록에서 primary(패키지 이름, 버전, 의존성 등 핵심 정보) 파일의 위치를 확인하고 받는다.
4. 받은 파일의 체크섬을 repomd.xml에 적힌 값과 비교한다. 체크섬은 파일 내용으로 계산한 고유한 값이라, 둘이 같으면 파일이 제대로 받아진 것이다.
5. 받은 파일을 내 서버의 캐시 디렉터리에 저장한다.
이때 "요청"은 웹 브라우저가 웹 페이지를 여는 것과 같은 HTTP 요청이다. 저장소 서버에는 dnf만을 위한 특별한 프로그램이 없다. nginx나 Apache 같은 평범한 웹 서버가 파일을 그대로 내려줄 뿐이다. 그래서 직접 요청해 볼 수도 있다.
```bash
curl http://dl.rockylinux.org/pub/rocky/9/BaseOS/x86_64/os/repodata/repomd.xml
```
이 명령을 실행하면 dnf가 받는 것과 똑같은 repomd.xml 내용이 화면에 출력된다.
## 캐시 디렉터리 구조
받은 메타데이터는 한 파일에 합쳐지지 않는다. 저장소마다 디렉터리가 하나씩 따로 만들어진다.
캐시(cache)는 한 번 받아 온 데이터를 다음에 다시 쓰려고 가까운 곳에 보관해 두는 것을 말한다. dnf의 캐시는 `/var/cache/dnf/`에 있다.
```plain text
/var/cache/dnf/
├── baseos-8b1c3f0e2a4d5f67/        ← BaseOS 저장소의 캐시
│   └── repodata/
│       ├── repomd.xml
│       └── 3a1f...-primary.xml.zst
├── appstream-1d2e3f4a5b6c7d8e/     ← AppStream 저장소의 캐시
│   └── repodata/ ...
├── epel-9f8e7d6c5b4a3f2e/          ← EPEL 저장소의 캐시
│   └── repodata/ ...
├── baseos.solv                     ← 검색용으로 변환한 파일
├── appstream.solv
└── epel.solv
```
디렉터리 하나에는 그 저장소에서 받은 repomd.xml과 primary 등의 메타데이터가 서버에 있던 모양 그대로 들어 있다. 파일 끝의 `.gz`, `.zst`는 압축 형식이다. 서버에서 압축된 상태로 받아 그대로 보관한다.
저장소별로 나눠 두는 이유는 갱신 때문이다. EPEL 저장소만 내용이 바뀌었다면 `epel-...` 디렉터리만 새로 받으면 된다. 모두 한 파일에 합쳐 두었다면 저장소 하나가 바뀔 때마다 전체를 다시 만들어야 한다.
한 가지 주의할 점이 있다. 위 경로는 root 권한으로 dnf를 실행할 때의 위치다. 일반 사용자로 `dnf list`처럼 조회만 하는 명령을 실행하면, dnf는 시스템 캐시를 건드리지 않고 `/var/tmp/dnf-사용자명-xxxx/` 같은 임시 디렉터리에 따로 캐시를 만든다. 캐시를 확인할 때 내용이 다르다면 어느 사용자로 실행했는지부터 확인하자.
참고로 rpm 파일 자체도 설치 직전에 잠깐 이 디렉터리 아래 `packages/`에 내려받는다. 기본 설정(`keepcache=0`)에서는 설치가 끝나면 지워진다.
## 디렉터리 이름 뒤의 해시는 왜 붙나
`baseos-8b1c3f0e2a4d5f67`에서 뒤쪽 문자열은 저장소 주소로 만든 해시값이다. 위조를 확인하려는 용도가 아니라, 캐시 디렉터리에 붙이는 이름표다.
해시는 어떤 데이터를 넣으면 정해진 길이의 문자열을 돌려주는 계산 방법이다. 같은 입력에는 항상 같은 결과가 나오고, 입력이 조금만 달라도 결과가 완전히 달라진다. dnf는 .repo 파일에 적힌 주소(baseurl, mirrorlist 또는 metalink)를 SHA-256이라는 방식으로 해시하고, 그 앞부분을 저장소 id 뒤에 붙인다.
이름표로 해시를 쓰는 이유는 세 가지다.
1. **주소가 바뀌면 캐시도 새로 만들기 위해서다.** 저장소 id가 `soojin`인 채로 주소를 A 서버에서 B 서버로 바꿨다고 하자. 디렉터리 이름이 `soojin`뿐이면 dnf가 B 서버를 보면서 A 서버에서 받은 옛 목록을 그대로 쓰는 사고가 날 수 있다. 해시를 붙이면 주소가 바뀌는 순간 디렉터리 이름도 바뀌어 새 캐시가 만들어진다.
2. **주소를 그대로 이름으로 쓸 수 없어서다.** 주소에는 `/`, `:`, `?` 같은 문자가 들어 있는데, `/`는 디렉터리 구분 기호라 파일 이름에 쓸 수 없다. 길이도 제각각이다. 해시로 바꾸면 항상 같은 길이의 안전한 문자열이 된다.
3. **언제 실행해도 같은 디렉터리를 찾아가기 위해서다.** 같은 주소는 항상 같은 해시가 나오므로, dnf를 다시 실행해도 기존 캐시를 정확히 찾아낸다.
해시는 흔히 "파일이 바뀌거나 위조되지 않았는지 확인하는 도구"로 소개된다. 앞에서 본 체크섬이 바로 그 용도다. 하지만 같은 성질 덕분에 이름표로도 널리 쓰인다. Git의 커밋 ID나 Docker 이미지 ID도 해시로 만든 이름표다. 해시의 두 가지 용도는 다음 글에서 따로 정리한다.
## .solv 파일: 저장은 따로, 검색은 합쳐서
`.solv` 파일은 primary.xml을 빠르게 읽을 수 있는 형태로 바꿔 둔 파일이다. dnf는 검색할 때 이 파일들을 메모리에 모아 하나로 합친다.
primary.xml은 사람이 읽을 수 있는 텍스트(XML) 형식이다. 사람이 보기에는 편하지만, 프로그램이 수만 개의 패키지 정보를 매번 처음부터 읽고 해석하기에는 느리다. 그래서 dnf는 메타데이터를 처음 받을 때 libsolv라는 라이브러리(여러 프로그램이 가져다 쓰는 기능 모음)를 이용해 컴퓨터가 바로 읽을 수 있는 바이너리 형식으로 바꿔 둔다. 그 결과가 `저장소id.solv` 파일이다. 파일 목록 정보는 `저장소id-filenames.solvx`처럼 따로 만들어지기도 한다.
`dnf install nginx`를 실행하면 다음 일이 일어난다.
1. 사용 중인 모든 저장소의 `.solv` 파일을 읽는다.
2. 메모리 안에 모든 저장소의 패키지가 들어간 하나의 큰 목록(패키지 풀)을 만든다.
3. 그 목록에서 nginx와 의존성을 한 번에 계산한다.
정리하면 **저장은 저장소별로 따로, 검색은 메모리에서 합쳐서** 한다. 저장을 나눠야 갱신이 가볍고, 검색을 합쳐야 여러 저장소에 걸친 의존성도 한 번에 풀 수 있다. 예를 들어 EPEL의 어떤 패키지가 BaseOS의 라이브러리를 필요로 해도, 하나의 목록 안에서 바로 찾아 연결할 수 있다.
## 캐시는 언제 갱신되나
dnf는 명령을 실행할 때마다 메타데이터를 새로 받지 않는다. 캐시의 유효 기간이 지났을 때만 저장소 서버에 다시 물어본다.
유효 기간은 `metadata_expire` 설정으로 정하며 기본값은 48시간이다. `/etc/dnf/dnf.conf`에서 전체 기본값을, .repo 파일의 섹션에서 저장소별 값을 바꿀 수 있다.
유효 기간이 지나면 dnf는 이렇게 판단한다.
1. repomd.xml만 먼저 다시 받는다. 크기가 작아서 금방 받는다.
2. 새 repomd.xml에 적힌 체크섬을 캐시에 있는 값과 비교한다.
3. 같으면 저장소 내용이 그대로라는 뜻이므로 캐시를 계속 쓴다. 다르면 바뀐 파일만 새로 받는다.
repomd.xml을 제외한 메타데이터 파일은 이름 앞에 체크섬이 붙어 있다. 내용이 바뀌면 파일 이름도 바뀌므로, 목차인 repomd.xml 하나만 비교해도 무엇이 바뀌었는지 알 수 있다.
갱신 시점을 직접 조절하는 명령도 있다.

Rocky Linux에는 `dnf-makecache.timer`라는 예약 작업도 있다. 서버가 켜져 있는 동안 주기적으로 `dnf makecache`를 실행해, 사용자가 명령을 칠 때 기다리는 시간을 줄여 준다.
실무에서 자주 만나는 상황은 이렇다. 저장소에 새 패키지를 올렸는데 다른 서버에서 `dnf install`을 하면 "패키지를 찾을 수 없다"고 나온다. 캐시가 아직 유효해서 옛 목록을 보고 있기 때문이다. 이럴 때 `dnf --refresh` 또는 `dnf clean metadata`를 쓰면 새 목록을 받아 온다.
## 직접 확인하기
아래 명령을 차례로 실행하면 이 글의 내용을 모두 눈으로 확인할 수 있다. 캐시 디렉터리를 보려면 `sudo`가 필요하다.
```bash
# 1. 메타데이터를 받아 캐시 만들기
sudo dnf makecache

# 2. 저장소별 캐시 디렉터리와 .solv 파일 보기
ls /var/cache/dnf/

# 3. 한 저장소의 캐시 안 들여다보기
ls /var/cache/dnf/appstream-*/repodata/

# 4. 캐시에 저장된 repomd.xml 읽기
cat /var/cache/dnf/appstream-*/repodata/repomd.xml

# 5. 같은 파일을 저장소 서버에서 직접 받아 비교하기
curl -s http://dl.rockylinux.org/pub/rocky/9/AppStream/x86_64/os/repodata/repomd.xml | head -20

# 6. 저장소별 주소와 캐시 상태 보기
dnf repolist -v
```
4번과 5번의 결과가 같다면 "캐시는 서버의 파일을 그대로 받아 둔 것"이라는 점을 확인한 셈이다. 다르다면 서버 쪽이 그사이 갱신된 것이다. `dnf --refresh makecache`를 실행한 뒤 다시 비교해 보자.
## 정리
이 글에서 다룬 내용을 다섯 줄로 줄이면 다음과 같다.
1. repomd.xml은 저장소 운영자가 `createrepo_c`로 만들어 서버에 올려 둔 목차다. dnf는 읽기만 한다.
2. dnf는 저장소마다 repomd.xml을 먼저 받고, 거기 적힌 primary 등을 이어서 받는다.
3. 받은 메타데이터는 `/var/cache/dnf/저장소id-해시/`에 저장소별로 따로 저장된다. 해시는 주소로 만든 이름표다.
4. 검색할 때는 저장소별 `.solv` 파일을 메모리에서 하나로 합쳐 의존성까지 한 번에 계산한다.
5. 캐시는 기본 48시간 동안 유효하고, 지나면 repomd.xml의 체크섬을 비교해 바뀐 것만 다시 받는다.
다음 글에서는 이번 글에 두 번 등장한 해시를 따로 다룬다. 같은 해시가 캐시 디렉터리에서는 이름표로, repomd.xml과 primary.xml에서는 파일 검증 도구로 쓰인다. 그리고 해시만으로는 막을 수 없는 위조를 GPG 서명이 어떻게 막는지도 함께 살펴본다.
